# 설계: 타이틀 코드가 커널 대기가 아닌 대기를 알리는 C API (issue #87)

상태: 설계. 소비자: reexec/reCT3#52. 이전: [i068 ADXM 잠금](20261016-i068-adxm-lock.md).

## 1. 요구사항

게스트 잠금을 쥔 스레드는 기록되는 대기(`NoteWaitBegin`/`NoteWaitEnd`: 커널 대기, 지연, 수직 귀선) 동안 자기 게스트 잠금을 내려놓는다. 그래서 Xbox에서 쥔 스레드가 막혀 있을 때처럼, 낮은 스레드가 안으로 들어갈 수 있다. 그런데 타이틀 코드는 커널 대기가 아닌 대기에 대해 같은 일을 할 방법이 없다. 두 함수는 C++ `rexbox::runtime`에만 있다.

Crazy Taxi 3의 CRI 핸드셰이크 `000B3060`(SVM 콜백 5)이 이 경우다.
* 플래그를 세우고, ADXM safe thread가 플래그를 지울 때까지 `SetThreadPriority`/`ResumeThread`를 되풀이한다.
* Xbox에서는 우선순위가 올라간 safe thread가 곧바로 호출자를 선점했다.
* 호스트에서는 호출자가 CRI ADXM 게스트 잠금을 쥔 채 돈다. safe thread의 서버 실행은 같은 잠금을 기다리므로 플래그를 지우지 못한다.
* 그래서 교착이 생기고, 2초 게스트 잠금 시한으로만 풀렸다가 되풀이된다.

## 2. 설계

`include/rexbox/runtime/guest_lock.h`의 C 부분에 두 함수를 더한다.

```c
/* The calling thread waits for another guest thread in a way that is not a
 * kernel wait (a spin on a flag, say). Its guest locks are put down until
 * rexbox_guest_wait_end, and the stall report shows `what` (static storage). */
void rexbox_guest_wait_begin(const char* what);
void rexbox_guest_wait_end(void);
```

* 구현은 `runtime::NoteWaitBegin(what, nullptr, 0, false, -1)`과 `runtime::NoteWaitEnd()`를 부른다. 그래서 잠금 내려놓기·다시 잡기, 중첩 규칙(바깥쪽 대기만), stall 보고, #80의 대기 합계가 커널 대기와 똑같이 동작한다.
* `guest_lock.h`가 C에서도 읽히므로 `extern "C"` 안에 둔다. 정의는 `guest_lock.cpp`에 둔다.
* 짝이 맞지 않는 `end`는 지금 `NoteWaitEnd`처럼 다루어진다(깊이 0이면 아무것도 하지 않는다).

## 3. 검증

* kernel probe에 짧은 확인을 더한다. 잠금을 쥔 스레드가 `rexbox_guest_wait_begin` 안에 있는 동안 다른 스레드가 같은 잠금에 들어갈 수 있고, `end` 뒤에는 다시 쥔다.
* CTest. reCT3#52의 수정으로 숨긴 데모 묶음을 확인한다.

# Design: a C API for title code to announce a wait that is not a kernel wait (issue #87)

Status: design. Consumer: reexec/reCT3#52. Earlier: [i068 ADXM lock](20261016-i068-adxm-lock.md).

## 1. Requirement

A guest-lock holder puts its guest locks down for the length of every noted wait (`NoteWaitBegin`/`NoteWaitEnd`: kernel waits, delays, vertical blanks), so a lower thread can run inside, as it could on the Xbox while the holder was blocked. Title code has no way to do the same for a wait that is not a kernel wait: both functions exist only in C++ `rexbox::runtime`.

Crazy Taxi 3's CRI handshake `000B3060` (SVM callback 5) is such a case:
* it sets a flag and repeats `SetThreadPriority`/`ResumeThread` until the ADXM safe thread clears the flag;
* on the Xbox the raised safe thread preempted the caller at once;
* on the host the caller spins while holding the CRI ADXM guest lock, and the safe thread's server pass waits for that same lock, so it cannot clear the flag;
* the result is a deadlock, broken only by the 2 s guest-lock timeout, and repeated.

## 2. Design

Two functions join the C part of `include/rexbox/runtime/guest_lock.h`:

```c
/* The calling thread waits for another guest thread in a way that is not a
 * kernel wait (a spin on a flag, say). Its guest locks are put down until
 * rexbox_guest_wait_end, and the stall report shows `what` (static storage). */
void rexbox_guest_wait_begin(const char* what);
void rexbox_guest_wait_end(void);
```

* They call `runtime::NoteWaitBegin(what, nullptr, 0, false, -1)` and `runtime::NoteWaitEnd()`, so putting the locks down and picking them up, the nesting rule (outermost wait only), the stall report and #80's wait totals behave exactly as for a kernel wait.
* `guest_lock.h` is read from C too, so they go inside `extern "C"`; the definitions go in `guest_lock.cpp`.
* An unpaired `end` is handled as `NoteWaitEnd` handles it today (nothing at depth 0).

## 3. Verification

* A short check in the kernel probe: while a lock holder is inside `rexbox_guest_wait_begin`, another thread can enter the same lock, and after `end` the holder has it again.
* CTest; reCT3#52's fix checked with hidden demo batches.
