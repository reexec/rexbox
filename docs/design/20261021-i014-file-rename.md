# 설계: 파일 이름 바꾸기 `FileRenameInformation` (issue #14)

## 1. 요구사항

소비자 reexec/reCT3#9: 타이틀이 디스크의 큰 자산을 캐시 파티션에 임시 이름(`Z:\tmp`)으로 복사한 뒤 XAPI `MoveFileEx`로 최종 이름(`Z:\_<자산>`)으로 바꾸고, 그 이름으로 다시 연다. rexbox의 `NtSetInformationFile`은 class 10을 `class 10 unsupported`로 보고하고 `STATUS_INVALID_PARAMETER`를 돌려주므로 최종 파일이 생기지 않고, 이어지는 열기가 `STATUS_OBJECT_NAME_NOT_FOUND`로 실패한다. 그 자산(도시 지형)은 그려지지 않는다.

XAPI `MoveFileEx`가 하는 일(4531 라이브러리의 lift된 코드에서 **확인됨**):

1. 원본을 `NtOpenFile(DELETE | SYNCHRONIZE, RootDirectory = ObDosDevicesDirectory())`로 연다.
2. 지역 `FILE_RENAME_INFORMATION`을 채운다: `ReplaceIfExists = dwFlags & MOVEFILE_REPLACE_EXISTING`, `RootDirectory = -3`(`\??\`), `FileName = RtlInitAnsiString(새 이름)`.
3. `NtSetInformationFile(handle, &iosb, &info, 0x10, 10)` 뒤 `NtClose`.

## 2. 구조 (Xbox, 32비트)

| 오프셋 | 필드 | 비고 |
|---|---|---|
| +0 | `BOOLEAN ReplaceIfExists` | 3바이트 패딩 |
| +4 | `HANDLE RootDirectory` | 0, `-3`(`\??\`), `-4`(`\BaseNamedObjects\`) 또는 디렉터리 핸들 |
| +8 | `OBJECT_STRING FileName` | `Length`(+8), `MaximumLength`(+10), `PCHAR Buffer`(+12). ANSI |

이름 해석 규칙은 `OBJECT_ATTRIBUTES`(`RootDirectory` + `ObjectName`)와 같으므로 같은 함수로 해석한다.

## 3. 설계

* `ObjectName(attributes)`의 루트 처리 부분을 `NameRelativeTo(root, name)`으로 떼어 두 곳에서 쓴다.
* `RenameFile(file, info)`(class 10):
  1. 파일·디렉터리 객체가 아니면 `STATUS_INVALID_PARAMETER`.
  2. 새 이름을 `VfsResolve`. 장치 밖이거나 원시 장치면 `STATUS_OBJECT_PATH_NOT_FOUND`. 원본이나 대상이 읽기 전용 장치면 `STATUS_ACCESS_DENIED`. 대상의 부모 디렉터리가 없으면 `STATUS_OBJECT_PATH_NOT_FOUND`.
  3. 대상이 원본과 같은 호스트 파일이면 아무것도 하지 않고 성공한다.
  4. 대상이 있을 때: `ReplaceIfExists`가 0이면 `STATUS_OBJECT_NAME_COLLISION`, 대상이 디렉터리면 `STATUS_ACCESS_DENIED`. 아니면 대상을 지운다(지우지 못하면, 예를 들어 다른 핸들이 열고 있으면 `STATUS_ACCESS_DENIED`).
  5. 같은 호스트 파일을 가리키는 **모든** 열린 핸들의 스트림을 닫고(호스트 Windows는 열린 파일의 이름을 바꾸지 못한다), `fs::rename` 뒤 새 경로로 다시 연다. 실패하면 옛 경로로 다시 열고 `STATUS_ACCESS_DENIED`. 스트림 객체는 그대로 두고 `close`/`open`만 하므로 그 `shared_ptr`을 쥔 쪽은 영향이 없다. 위치는 객체의 `position`에 있으므로 유지된다.
  6. 성공하면 그 핸들들의 `host_path`, `xbox_path`를 새 이름으로 바꾼다. `delete_on_close`는 그대로 따라간다.
* 핸들 표는 `dispatcher` 잠금 아래에서 훑는다. 이름 바꾸기 자체도 그 잠금 안에서 끝낸다(짧은 호스트 파일 연산 하나).
* `REXBOX_TRACE_FILES`가 있으면 `[kernel] rename <옛 이름> -> <새 이름> -> <상태>`를 출력하고, 없으면 실패만 한 번 보고한다(열기와 같은 규칙).

## 4. 검증

* `rexbox_kernel_probe`: 파티션에 파일을 만들어 쓰고, 핸들을 연 채 `\??\`가 아닌 절대 이름과 디렉터리 루트로 각각 이름을 바꾼 뒤 (a) 새 이름으로 열리고 내용이 같은지, (b) 옛 이름은 `STATUS_OBJECT_NAME_NOT_FOUND`인지, (c) 이름을 바꾼 핸들로 계속 읽을 수 있는지, (d) `ReplaceIfExists = 0`에서 충돌, 1에서 덮어쓰기, (e) 읽기 전용 장치(`D:`)에서 거부를 확인한다.
* 소비자 실행: 캐시 파일이 최종 이름으로 생기고 그 뒤 열기가 성공해야 한다.

# Design: file rename, `FileRenameInformation` (issue #14)

## 1. Requirement

Consumer reexec/reCT3#9: the title copies a large disc asset to the cache partition under a temporary name (`Z:\tmp`), renames it with XAPI `MoveFileEx` to its final name (`Z:\_<asset>`), and opens it by that name. rexbox's `NtSetInformationFile` reports `class 10 unsupported` and returns `STATUS_INVALID_PARAMETER`, so the final file never exists, the next open fails with `STATUS_OBJECT_NAME_NOT_FOUND`, and that asset (the city geometry) is not drawn.

What XAPI `MoveFileEx` does (**confirmed** in the lifted 4531 library code): it opens the source with `NtOpenFile(DELETE | SYNCHRONIZE, RootDirectory = ObDosDevicesDirectory())`; fills a local `FILE_RENAME_INFORMATION` with `ReplaceIfExists = dwFlags & MOVEFILE_REPLACE_EXISTING`, `RootDirectory = -3` (`\??\`) and `FileName = RtlInitAnsiString(new name)`; and calls `NtSetInformationFile(handle, &iosb, &info, 0x10, 10)`, then `NtClose`.

## 2. Layout (Xbox, 32-bit)

`BOOLEAN ReplaceIfExists` at +0 (three bytes of padding); `HANDLE RootDirectory` at +4 (0, `-3` for `\??\`, `-4` for `\BaseNamedObjects\`, or a directory handle); `OBJECT_STRING FileName` at +8 (`Length` +8, `MaximumLength` +10, `PCHAR Buffer` +12; ANSI). Names resolve exactly like `OBJECT_ATTRIBUTES` (`RootDirectory` + `ObjectName`), so the same function resolves both.

## 3. Design

* The root handling of `ObjectName(attributes)` becomes `NameRelativeTo(root, name)`, used by both.
* `RenameFile(file, info)` (class 10): (1) `STATUS_INVALID_PARAMETER` unless the object is a file or directory. (2) Resolve the new name with `VfsResolve`: `STATUS_OBJECT_PATH_NOT_FOUND` outside any device or on a raw device, `STATUS_ACCESS_DENIED` when the source or target device is read-only, `STATUS_OBJECT_PATH_NOT_FOUND` when the target's parent directory is missing. (3) A target that is the source's host file succeeds with nothing done. (4) An existing target gives `STATUS_OBJECT_NAME_COLLISION` when `ReplaceIfExists` is 0 and `STATUS_ACCESS_DENIED` when it is a directory; otherwise it is removed (`STATUS_ACCESS_DENIED` when that fails, for example while another handle holds it). (5) The streams of **every** open handle on the same host file are closed (a Windows host cannot rename an open file), `fs::rename` runs, and they reopen on the new path; on failure they reopen on the old path and the result is `STATUS_ACCESS_DENIED`. The stream objects stay and are only `close`d and `open`ed, so whoever holds their `shared_ptr` is unaffected; positions live in each object's `position` and are kept. (6) On success those handles take the new `host_path` and `xbox_path`; `delete_on_close` follows the file.
* The handle table is walked under the `dispatcher` lock, and the rename finishes inside it (one short host file operation).
* With `REXBOX_TRACE_FILES` it prints `[kernel] rename <old> -> <new> -> <status>`; without it only failures are reported, once (the same rule as opens).

## 4. Verification

* `rexbox_kernel_probe`: create and write a file on a partition, and with its handle open rename it by an absolute name and by a directory-relative name; check (a) the new name opens with the same contents, (b) the old name gives `STATUS_OBJECT_NAME_NOT_FOUND`, (c) the renamed handle still reads, (d) a collision with `ReplaceIfExists = 0` and a replacement with 1, (e) a refusal on a read-only device (`D:`).
* Consumer run: the cache file appears under its final name and the following open succeeds.
