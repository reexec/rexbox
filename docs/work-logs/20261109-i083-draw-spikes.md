# 작업 로그: 일부 draw가 많은 프레임에서 그리기 단계가 두 배가 됨 (issue #83)

작업 지시: [20261108-i083](../work-orders/20261108-i083-draw-spikes.md) · 설계: [20261108-i083](../design/20261108-i083-draw-spikes.md)

## 한 일

1. 1단계 `ef357d5`: 느린 프레임 줄에 단계별 시간, 그 프레임의 정점 비교·업로드 양, `oncpu`를 붙였다.
   * `oncpu`는 플랫폼의 정밀 스레드 CPU 시간 `ThreadCpuPreciseNanoseconds`다. Windows는 `QueryThreadCycleTime`, Linux는 `CLOCK_THREAD_CPUTIME_ID`를 쓴다.
   * Windows의 사이클→ns 비율은 켤 때 10 ms 바쁜 루프로 정한다. 그동안 스레드가 선점되면 비율이 조금 커질 수 있다. 진단에는 받아들일 만하다(검토 메모).
2. 측정: 주행 중 느린 draw 프레임은 경주 시작 구간에 몰려 있었다. 튀는 단계는 setup(평균 6.1 ms)이었고, 원인은 작은 DXT 텍스처를 만들 때의 GL 시간 3~5 ms(최대 13.7 ms)였다.
3. 2단계 a `926a76d`: 2D 텍스처를 `glTexStorage2D`로 한 번에 정하고, 데이터는 `glCompressedTexSubImage2D`/`glTexSubImage2D`로 올린다.
   * 진입점이 없거나, 3D 텍스처이거나, 레벨이 게스트 메모리 밖이면 예전 경로를 쓴다.
   * 크기·형식·레벨 수가 그대로인 재업로드는 저장소를 다시 정하지 않는다.
   * 느린 프레임 상세는 GL 시간을 저장소와 데이터로 나눈다.
4. 2단계 b(풀)는 하지 않기로 했다(설계 §3의 결정).
5. 역할: 코드는 Antigravity, 설계·검토·측정·문서는 Claude가 했다.

# Work log: draw phases doubling in some draw-heavy frames (issue #83)

Work order: [20261108-i083](../work-orders/20261108-i083-draw-spikes.md) · Design: [20261108-i083](../design/20261108-i083-draw-spikes.md)

## Done

1. Step 1, `ef357d5`: slow-frame lines gained the per-phase time, the frame's vertex-compare and upload volume, and `oncpu`.
   * `oncpu` is the platform's precise thread CPU time, `ThreadCpuPreciseNanoseconds`: `QueryThreadCycleTime` on Windows, `CLOCK_THREAD_CPUTIME_ID` on Linux.
   * On Windows the cycles-to-ns ratio is set by a 10 ms busy loop at enable time; if the thread is preempted meanwhile the ratio may come out a little high, which is acceptable for a diagnostic (review note).
2. Measurement: driving's slow draw-heavy frames clustered at the race start. The phase that spiked was setup (6.1 ms on average), and the cause was 3–5 ms (up to 13.7 ms) of GL time when making a small DXT texture.
3. Step 2a, `926a76d`: 2D textures get their storage at once with `glTexStorage2D`, and the data goes up with `glCompressedTexSubImage2D`/`glTexSubImage2D`.
   * Without the entry points, for 3D textures, or when a level lies outside guest memory, the old path is used.
   * A re-upload with the same size, format and level count does not set the storage again.
   * The slow-frame detail splits the GL time into storage and data.
4. Step 2b (the pool) was not done (the decision in design section 3).
5. Roles: Antigravity wrote the code; Claude designed, reviewed, measured and wrote the documents.

* rexbox CTest 4/4; reCT3 Win32 x86 Release, CTest 7/7. All of these are the coder's report.

* No GL errors. A capture of frame 3600 while driving showed the buildings, palm trees, car, HUD and road textures all correct.
