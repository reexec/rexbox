# 작업 로그: 프레임당 GL 드라이버 시간 (issue #76)

작업 지시: [20261107-i076](../work-orders/20261107-i076-gl-call-time.md) · 설계: [20261107-i076](../design/20261107-i076-gl-call-time.md)

## 한 일

1. `REXBOX_GL_CALLS=time`을 더했다(`6e553d7`, Antigravity 구현, Claude 설계·검토).
   * 진입점마다 설치되는 기존 래퍼가 `steady_clock`으로 호출 시간을 잰다. 반환값이 있는 진입점과 없는 진입점을 모두 다룬다.
   * 시작할 때 빈 `now()` 쌍 10000번으로 타이머 비용을 잰다.
   * 프로파일 창마다 `gl time` 줄(합계, 호출 수, 타이머 추정치, cpu 대비 비율, 시간이 많은 진입점 16개)을 출력한다.
   * `TakeGlCallCounts`가 이름·횟수·시간을 함께 돌려준다. 변수가 없거나 `1`이면 동작은 그대로다.
2. 검토에서 짚은 점: 잰 값은 호출 안의 벽시계 시간이다. 그래서 드라이버가 기다린 시간도 들어가고, cpu 대비 비율은 100%를 넘을 수 있다. 진단 목적에는 그대로 둔다.
3. ARCHITECTURE의 환경 변수 목록을 `REXBOX_GL_CALLS=1|time`으로 고쳤다.

## 검증

* rexbox CTest 4/4, Python 테스트 6/6. reCT3 Win32 x86 Release 빌드 경고 0, CTest 7/7. 모두 코더 보고다.
* reCT3 West Coast 주행(`REXBOX_D3D8_PROFILE=600`, 21:9, 렌더 배율 4, MSAA 16x):

| draw/프레임 | fps | cpu ms/프레임 | GL ms/프레임 | `glBindVertexArray` ms (호출) | 그 밖의 GL ms |
|---|---|---|---|---|---|
| 644 | 57.5 | 5.68 | 0.89 | 0.09 (594) | 0.80 |
| 900 | 59.0 | 7.55 | 1.41 | 0.89 (870) | 0.52 |
| 999 | 50.4 | 10.13 | 3.39 | 2.75 (951) | 0.64 |
| 1584 | 30.6 | 17.37 | 7.44 | 6.66 (1528) | 0.78 |

* 타이머 비용은 1584 draw에서 프레임당 0.35 ms로 추정된다. 시간 측정 없이 돈 같은 주행은 밀집 구간에서 41.5 fps(1272 draw), 29.9 fps(1695 draw)였다. 진단 자체의 교란은 작다.
* 결론(reCT3#41): 밀집 장면의 GL 드라이버 시간은 거의 전부 `glBindVertexArray`다.
  * 바인드 한 번의 비용이 draw 수와 함께 1 µs에서 4.4 µs로 커진다.
  * #23 이후 캐시된 정점 구간마다 VAO가 하나씩이고, 모든 VAO의 요소 바인딩이 draw마다 `glBufferSubData`로 쓰는 하나의 인덱스 스트림 버퍼를 가리킨다. 이것이 유력한 원인이다(**추정**).
  * 렌더 스레드로는 이 비용이 줄지 않는다. 다음 단계는 VAO 사용 방식(별도 issue)이다.

## 남은 것

* VAO 바인드 비용의 원인 확인과 수정(새 issue).

# Work log: GL driver time per frame (issue #76)

Work order: [20261107-i076](../work-orders/20261107-i076-gl-call-time.md) · Design: [20261107-i076](../design/20261107-i076-gl-call-time.md)

## Done

1. Added `REXBOX_GL_CALLS=time` (`6e553d7`, implemented by Antigravity, designed and reviewed by Claude).
   * The existing per-entry-point wrapper times each call with `steady_clock`, for entry points with and without a return value.
   * At start-up 10000 empty `now()` pairs give the timer's own cost.
   * Each profile window prints a `gl time` line: the total, the number of calls, the timer estimate, the share of cpu, and the 16 entry points with the most time.
   * `TakeGlCallCounts` returns the name, count and time together. Without the variable, or with `1`, nothing changes.
2. Noted in review: the figure is wall-clock time inside the call, so it includes time the driver waited, and its share of cpu can exceed 100%. That is left as is for a diagnostic.
3. ARCHITECTURE's list of environment variables now reads `REXBOX_GL_CALLS=1|time`.

## Verification

* rexbox CTest 4/4 and Python tests 6/6; reCT3 Win32 x86 Release with 0 warnings and CTest 7/7. All of these are the coder's report.
* A reCT3 West Coast drive (`REXBOX_D3D8_PROFILE=600`, 21:9, render scale 4, MSAA 16x):

| Draws/frame | fps | cpu ms/frame | GL ms/frame | `glBindVertexArray` ms (calls) | Other GL ms |
|---|---|---|---|---|---|
| 644 | 57.5 | 5.68 | 0.89 | 0.09 (594) | 0.80 |
| 900 | 59.0 | 7.55 | 1.41 | 0.89 (870) | 0.52 |
| 999 | 50.4 | 10.13 | 3.39 | 2.75 (951) | 0.64 |
| 1584 | 30.6 | 17.37 | 7.44 | 6.66 (1528) | 0.78 |

* The timer's cost is estimated at 0.35 ms per frame at 1584 draws. The same drive without timing ran at 41.5 fps (1272 draws) and 29.9 fps (1695 draws) in the dense stretches, so the diagnostic's own disturbance is small.
* Conclusion (reCT3#41): in dense scenes nearly all GL driver time is `glBindVertexArray`.
  * One bind costs more as draws grow, from 1 µs to 4.4 µs.
  * Since #23 each cached vertex range has its own VAO, and every VAO's element binding points at the one index stream buffer that each draw writes with `glBufferSubData`. That is the likely cause (**inferred**).
  * A render thread would not reduce this cost. The next step is how the VAOs are used (a separate issue).

## Remaining

* Confirming and fixing the cause of the VAO bind cost (new issue).
